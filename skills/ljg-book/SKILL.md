# ljg-book：让读者跟着一本书改变一次看法

一本书真正难讲的地方，通常不在名词多，而在作者为什么要改变原来的看法。

从一件简单的事开始。先把抽象关系压成一个核心动作或状态变化，再找一个能让这次变化真实发生的场景。让读者照自己最自然的理解想一次、做一次。接着把书里的事件、案例、论证或人物后果放进来。哪里解释不通，哪里就需要改。改完再跑一次。新的结果又会把人带到下一件事。

读者最后记住的，不是一套分析框架。他记住的是：自己一开始站在哪里，书中的什么东西逼他移动，移动以后又看见了什么。

## Workflow Routing

| 输入 | 必读 | 输出 |
|---|---|---|
| 书名 | 找到可靠材料后读 `ReadingGuide.md` | 保存 Markdown 笔记 |
| PDF、EPUB、正文、样章、旧笔记 | 先读原文，再读 `ReadingGuide.md` | 保存 Markdown 笔记 |
| 用户明确只要口头解释 | `ReadingGuide.md` | 不写文件，按同一路径讲 |

写 Markdown 文件时再读 `references/template.md`。每次任务都从 `references/coverage-map.md` 建立后台记录；材料薄时只填公共字段，全文材料则填完全部覆盖项。

默认保存到 `~/Documents/notes/`。文件名沿用 Denote：`{YYYYMMDDTHHMMSS}--拆书-{书名}__book.md`；时间戳用 `date +%Y%m%dT%H%M%S` 生成。

## Gotchas

- *后台模型不能长成前台目录。* x、R、f、E 用来检查变化发生在哪里，成品标题只写事情本身。
- *简单场景不是暖场。* 它要真的承受书中的证据，产生结果，再把读者推向下一场景。
- *场景不是概念的装饰图。* 角色、动作、变化方向、结果与边界要能承载同一机制；删掉解释后，场景本身仍应露出一部分关系。
- *一条张力不等于只能用一个例子。* 历史、社会与文学作品常需要多个场景；场景可以换，张力不能散。
- *变化不总是加入一个新概念。* 作者可能换了观察对象、证据标准、行动方式，也可能只是保留了一个无法消掉的矛盾。
- *术语不负责开路。* 先让读者看见缺少它会解释不了什么，再给名字。
- *转折必须由书来推动。* 不为叙事顺滑编造作者没有面对的反方或失败。
- *例子帮助理解，不替作者作证。* 原书证据、作者解释和讲解者的简化推演要分开。
- *文学作品不硬改成方法书。* 人物、关系、世界或意象的变化本身就可以是认识的推进。
- *材料薄就少说。* 材料等级留在后台记录；成品中的每个判断只说到证据真正支持的位置。

## 讲解引擎

先找出贯穿全书的一条张力。它可以是一个两难选择、一个反复失败的办法、一个人物无法摆脱的矛盾，也可以是作者一直追问却不断改写的问题。

然后找一件最简单的事，让读者站进去：

选场景前，先把要讲的关系改写成「什么一变，什么随之怎样变」。这就是核心动作或变化。候选场景不必与原书共享表面名词，但角色、动作、变化方向、结果与失效边界要一一对得上。对不上，它只是一个好听的类比。

场景至少要能运行一次可见变化：原状态中只改变一个关键条件或动作，结果随之改变；读者看见变化以后，马上给它名字。若还要推进，优先看同一场景能否再改变一个条件；承载不了就换场景，但仍由同一条张力连接。

```text
当前处境 x_t
    ↓
读者原有的理解 R_t 与反应 f_t 运行
    ↓
书中的事件、案例、论证或人物后果由 E_t 检验
    ↓
证据或张力迫使 x、R、f、E 中至少一项更新
    ↓
新的结果成为下一场景 x_(t+1)
```

这里的字母只在后台使用：

- `x`：人实际站着的处境，包括关系、时间、资源与限制。
- `R`：人怎样理解眼前的事，用什么区分和标准判断。
- `f`：在这种理解下，人会怎样选择、行动或克制。
- `E`：什么算证据，书中的什么结果有资格检验前面的理解。

每次回流只问三件事：

1. 这一次原来的理解或反应得到了什么结果？
2. 书中的哪条证据、事件或后果让这个结果站不住？
3. x、R、f、E 中究竟哪一项被改写，改完以后下一场景为什么会出现？

这个过程可以发生一次，也可以发生多次。篇幅由因果链决定，不由模板决定。

## 不同书，改写的位置不同

| 书型 | 常见变化 | 怎样推进 |
|---|---|---|
| 分析、理论 | `R` 或 `E` | 同一现象换一种区分或证据标准，原判断随之改变 |
| 方法、实践 | `f`，有时连同 `E` | 旧做法产生具体后果，新做法再接受结果检验 |
| 历史、社会 | 多个 `x`，`R` 逐渐累积 | 同一张力穿过不同时间和群体，条件变化揭示机制 |
| 技术、科学 | 问题条件、机制链与检验 | 从最小可运行模型起步，让故障或反例逼出下一层机制 |
| 文学、哲学 | 人物或世界的 `x` 与 `R` | 经历改变原来的命名；结尾可以保留矛盾，不强造方法 |

书型只是起手判断。一本书可能同时改写几项，按真正起作用的关系写。

## 一条张力，若干回流，一次返程

这是后台构图，不是可见提纲。

**一条张力**：用一句话写清什么东西一直没有被解决。它负责筛选材料。与这条张力无关的精彩段落，不进主线。

**若干回流**：让旧理解运行，得到结果；让书里的证据或事件施压；改写一项关键关系；把新结果带进下一个场景。每次都要发生可见变化，不能只多一段定义。

**一次返程**：结尾回到开头的人或处境。此时不再加新概念，只写同一件事为什么已经不能照旧理解。返程可以落在新的判断、行动、观看方式、机制理解，也可以落在一个更准确的未决问题。

一本书未必有一个可摘出来的「最终发现」。只要读者能说清自己的看法在哪里被书改变，以及这种改变在什么条件下成立，讲解就完成了。

## 成文结构

标题从内容里长出来。用事件、变化或条件命名，让读者只看标题也能看见事情正在推进。

分析类书可以这样写：

```text
为什么换一种说法，选择就翻了
人先站在哪里，再看得到失
同一决定怎样重新问一遍
```

文学作品可以这样写：

```text
老师给的答案为什么进不了生活
河流怎样把矛盾放在一起
回到老师面前，他还需要答案吗
```

这两组只是语感示例。不要复制。一本书可以有两个标题，也可以有四五个；每出现一次真正的场景变化，才考虑换标题。

正文前的 `description` 在写完全文后补。它用一两句压缩这本书改变了什么看法，帮助检索，不承担导读目录的功能。

通常写 1000 到 1800 个汉字。短书可以更短，复杂书可以更长。字数只负责提醒是否失控，不能删掉理解所需的中间关系。

## 证据与边界

研究过程全部留在后台覆盖记录。成品不列研究清单，不展示材料等级。

需要限制结论时，把边界贴在相应判断后面：

- 有全文，就说明书内哪个案例、事件、论证或人物变化支撑这一步。
- 只有样章或可靠评论，就只写这些材料能支持的局部理解。
- 为了讲清而简化了场景，就说明哪些条件被保留，哪些只是推演。
- 反例改变结论时，直接在那一段改写结论，不把限制集中到末尾。

## 理解阻力

只有关系看不见时才画图：

| 关系 | 优先表达 |
|---|---|
| 前后步骤、状态变化 | 流程图或时间轴 |
| 循环、反馈、自我强化 | 回路图 |
| 层级、部分与整体 | 结构图 |
| 分布、边际变化、空间关系 | ASCII 曲线 |
| 两种机制反复对照 | 小表格 |
| 两三句话已经足够 | 纯文字 |

ASCII 图放进 Markdown 围栏代码块，宽度不超过 80 字符。一张足够。只把摘要换行排成图，不会帮助理解。

## 写作声音

- 先写人、物、动作和结果，再写抽象关系。
- 一段只推动一次变化。句子短而完整，主语清楚。
- 直说发生了什么。少写「作者提供了某种视角」「在这个意义上」。
- 转折跟着事情走，不按「首先、其次、最后」排队。
- 术语出现前，读者已经知道它解决什么；出现后，马上回到例子看结果。
- 公式若是最短解释就保留，下一句立刻说人话。
- 证据紧跟判断。边界紧跟证据。
- 不用「前言」「第 XX 章」等来源位置组织叙述。

## Quick Reference

1. 建立后台覆盖记录，写明材料等级、主要材料和能支持到哪里。
2. 全文材料再走完四类证据，列 5 到 12 个候选部件与反证。
3. 找出贯穿全书的一条张力，再写清其中的核心动作或状态变化。
4. 选一个读者能立即代入的最简单场景，检查角色、动作、方向、结果与边界是否对应。
5. 在原状态中只改变一个关键条件或动作，让旧理解或旧反应运行，写清可见结果。
6. 结果出现后再给关系命名，并用书内事件、案例、论证或后果暴露缺口。
7. 判断 x、R、f、E 中哪一项真正被改写，并把新结果带进下一场景。
8. 继续回流，直到这本书形成的判断、机制、观看方式或矛盾完整出现。
9. 回到开头，按内容变化命名标题，最后补 `description`。
10. 运行机械检查，再对照原文读回关键转折。

## Examples

**分析类书**

救援队要在两个方案中选一个。一个保证救下 200 人，另一个可能救下 600 人，也可能一个都救不了。多数人先选确定方案。把同一结果改成「会死多少人」，许多人又改选冒险方案。

旧解释说，人只是算错了概率。可概率没有变，选择却变了。真正被改写的是判断的参照：人先把说法感受成获得或损失，再比较结果，而损失带来的痛更强。回到救援方案，同一组数字为什么带出两种选择就看清了。下一次做重要决定，可以把得与失两种说法都写一遍，再看自己的答案是否翻转。

**文学作品**

一个年轻人不断向老师寻找智慧。他记住了许多答案，却发现这些话进了脑子，没有进入生活。离开老师以后，欲望、厌倦和失去一次次让旧答案失效。

河流没有再给他一个更好的结论。它让过去、现在和未来同时出现，原来互相冲突的经验可以被一个人一起听见。回到老师面前，他不再需要证明哪句话才是最终答案。改变的是他与答案的关系：智慧不再是可以转交的话，而是一个人怎样容纳自己走过的路。

## Completion

生成后读回确认：

- 每次任务都有独立后台覆盖记录；材料等级、主要材料和支持边界已经填写。
- 完整拆书走过问题、对象、机制、边界四类证据，并保留 5 到 12 个候选部件。
- 文件确实保存，frontmatter、`description` 与 Denote identifier 完整。
- 顶层标题来自具体事件、变化或条件，没有固定标题合同。
- 成品没有研究工作台、材料等级或 x/R/f/E 等内部标签。
- 开头是一件能想象的具体事情，旧理解或旧反应已经真实运行。
- 抽象关系的核心动作或变化已经说清；场景的角色、动作、方向、结果与边界能够对应。
- 场景至少完成一次「原状态 → 改一个条件或动作 → 可见结果 → 即时命名」；删掉解释后仍看得见一部分机制。
- 每次转折都由书内事件、案例、论证、人物后果或反例推动。
- 每次更新都让结果发生可见变化，并自然产生下一场景。
- 多个场景仍由同一条张力连接，没有为了覆盖内容而散开。
- 结尾回到开头，准确写出改变后的判断、机制、观看方式或未决张力。
- 方法书的做法接受了结果检验；文学作品没有被改成步骤清单。
- 证据、作者解释和讲解者推演分得清，边界贴着对应判断。
- 图表若存在，确实比短句更容易看懂，ASCII 宽度合格。

写入 Markdown 后运行：

```sh
bun {skill_dir}/scripts/validate_note.ts /absolute/path/to/note.md \
  --coverage /absolute/path/to/coverage-map.md
```

检查器负责结构、后台材料等级、Denote identifier、来源位置标签、图形宽度与完整拆书覆盖；场景与机制是否真的对应、讲解是否准确，仍要对照原文读回关键转折。
