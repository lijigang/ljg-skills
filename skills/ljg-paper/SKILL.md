# ljg-paper：让一个例子替读者想明白

它不复述摘要。它让一个不懂该领域的人先进入一件具体的事，看原来的理解怎样得出结果，又怎样被论文里的证据一步步改写。

术语不负责开路。正在发生的事负责。

## 后台讲解引擎

先找一件读者马上能想象的事。它要小，但不能删掉会改变论文结论的条件。让读者最自然的理解直接在这件事里运行，不给它起名字，也不预告它会失败。

写作者在后台把理解看成一个会回流的过程：

```text
x_t --[在 R_t 中运行 f_t]--> 结果
                               ↓
                         E_t 检查结果
                               ↓
                         证据或缺口出现
                               ↓
                       更新 x / R / f / E
                               ↓
                            x_{t+1}
```

- `x`：此刻真正摆在眼前的情况。
- `R`：我们把这件事放进什么关系和边界里理解。
- `f`：我们实际怎样处理、预测或干预它。
- `E`：我们凭什么判断结果对不对、够不够好。

论文不一定「增加一个概念」。它可能改写 `R`，换掉 `f`，让 `E` 看见原来漏掉的差异，也可能扩大可进入的 `x` 或可执行的 `f`。证据会暴露缺口，逼迫理解更新，并成为下一轮的起点。

| 论文主要贡献 | 后台主要看哪里改变 |
|---|---|
| 解释 / 理论 | `R`：哪些关系、边界或因果位置被重新安排 |
| 方法 / 干预 | `f`：处理动作怎样改变，结果为什么随之改变 |
| 测量 / 评测 | `E`：旧判断漏掉什么，新证据让什么变得可见；必要时也会改写 `R` |
| 资源 / 系统 | 可行的 `x` 或 `f`：原来进不去、做不到的范围怎样被打开 |

### 从后台判断走到可见动作

在动笔前，把中心贡献改写成一条读者能在同一例子里运行的动作链：

- 主角或对象是谁；
- 它处在什么条件；
- 原来的理解让它做什么；
- 原来期待什么，实际发生什么；
- 论文改了哪个动作、关系或判断尺度；
- 哪个可见结果最先改变。

其中任何一个承重关系若只能用论文术语回答，例子还没有准备好。先把术语拿掉，直到读者仍能看见谁做了什么、结果为何不同。技术对象的名字若不可省，可以出现一次，但不能拿名字代替它的作用。

这六项是备课检查，不是正文句式。成文时把它们自然写成一件正在发生的事，不按「条件是、期待是、实际是」逐格报答案。

### 跨过读者的熟悉度门

「论文里的具体案例」不一定对外行具体。模型名、数据集名、算法名和指标即使指向实物，读者仍可能不知道谁在做什么。第一段若需要先懂两个领域词才能复述，例子就还停在作者的世界里。

这时先找一个结构相同的熟悉场景。它不是随便打比方，而要保留论文机制里的角色、动作方向、反馈顺序和会改变结论的条件。学生交卷、医生看检查结果、顾客排队、工人调机器都可以；选哪一个取决于它能否忠实演出论文的因果关系。熟悉场景里的每个承重角色、动作和反馈都必须能映回论文对象及来源证据；无法映回的因果步骤要删除或明确标成讲解者推演。熟悉场景把关系演出来以后，再把论文对象放回同一位置，并在作用已经可见时命名。

读者在任一段都只承担一个新的承重概念。专有名词、模型型号、数据集和完整指标留在本次运行的证据台账，除非它们会改变读者的判断。证据台账必须是可读回的真实文件，每项写明来源位置、论文直接结果、它支持的正文判断，以及进入正文或留在后台的理由；无法出示台账时，不得声称证据已保留。正文保留支撑关键判断、竞争解释和边界所需的最小证据集，不设数字配额；留下的数字要回答「改动有没有改变结果」「改变有多大」或「边界在哪里」，而不是证明写作者读得很全。

例子有两种。严格保留角色、作用方向、反馈顺序和关键条件的简化案例，是**机制的缩小版**，可以替正文开路；只借一个形象帮助记忆的，是**装饰性类比**，只能在机制讲清以后出现。删掉术语后，前者仍能演出旧理解为何失效、新理解改变了什么；后者不能承担证明或推理。

`FX`、`x/R/f/E` 和这条回流链只供写作者校准。成文时不要出现「零号模型」「第一步」「更新 R」之类的讲解标签。正文只让读者看见：事情怎样发生，证据在哪里顶住了原来的理解，改动以后结果怎样变化。

正文通常有三个叙事运动：先让旧理解在具体事情里运行；再让证据迫使理解改变；最后把论文直接测过的条件变化放回同一场景，显出发现的边界。论文没有测到条件变化时，直接说「论文没有测到这里」，提出待验证问题即可，不靠推演补齐结构。它们不是三个固定章节。中间若有两个真实的因果转折，可以拆开；没有就不要凑数。

## Workflow Routing

| 输入 | 必读 | 输出 |
|---|---|---|
| arXiv、PDF、paper URL、本地论文 | `ReadingGuide.md` | 生成由论文内容命名的 Markdown 笔记 |
| 只有论文标题 | 找到可靠原文后读 `ReadingGuide.md` | 生成由论文内容命名的 Markdown 笔记 |
| 用户明确只要口头解释 | `ReadingGuide.md` | 不写文件，按同一路径讲 |

写 Markdown 文件时再读 `references/template.md`。所有生成的 Org 文件统一保存到 `~/Context/`；目录不存在时先创建，不再写入其他默认目录。

文件名沿用 Denote：`{YYYYMMDDTHHMMSS}--paper-{方法名或论文关键词}__paper.md`；时间戳用 `date +%Y%m%dT%H%M%S` 生成。

## Gotchas

- *别把内部方法写给读者看。* `FX` 和 `x/R/f/E` 只用于备课。正文写事情、证据和变化，不让读者先学习一套讲解框架。
- *例子不是装饰。* 它必须从开头一直用到作者的结论，并保留角色、作用方向、反馈顺序和关键条件。中途不断换例子，读者就看不见每次新增的东西究竟改变了什么。
- *领域对象不等于熟悉场景。* 「一个模型采样 16 条轨迹」对研究者很具体，对外行仍是一串术语。先让外行在熟悉角色和动作里看见同一关系，再映回论文对象。
- *不要先端出术语，再用故事解释术语。* 先让读者看见没有它会发生什么；在作用第一次变得可见的位置给出名字，然后立即放回同一例子重跑。
- *不要让证据台账溢进正文，也不要虚构台账。* 页码、完整指标、模型型号、全部对照属于核验层；正文只留下会改变判断的证据。台账必须真实保存并在交付前读回，否则删掉的证据就是丢失。完整不等于易懂。
- *不要用词项命中冒充通俗性验收。* 自动检查可以验证来源、数字和禁词，却不能因为正文出现了某个术语或某组指标就判定讲解成功。通俗性由新鲜读者的复述来验。
- *不要把动作链写成核对表。* 六个字段只防止漏掉关键关系。正文仍按事件自然展开，不逐项报「主角、条件、期待、实际」。
- *不要把旧四章换成新三章。* 固定的是后台的叙事运动，不是可见标题。标题必须从论文里的事件、变化或条件长出来。
- *不要把所有进展都写成「加入新概念」。* 先判断作者改变的是情况、关系、做法、判断尺度，还是可行范围。
- *不要为了递进而编问题。* 每个问题都要来自论文的问题设定、方法对照、实验结果、测量盲点或资源限制。
- *不要为了边界而编反例。* 优先使用论文里的对照、消融、失败样本或条件变化。论文没有直接材料时，写清「论文没有测到这里」并提出待验证问题；不必制造推演场景来补齐结构。
- *新概念不一定一次只来一个。* 几个变量若本来就同时作用，用并排案例、状态表或一张关系图一起讲。不要硬编虚假的先后。
- *并非每篇论文都推翻旧理论。* 方法论文可能只是把事情做得更好；评测论文可能只是让差异变得可见；资源论文可能只是让原来做不到的事变得可做。
- *一个例子能帮助理解，不能证明普遍成立。* 论文证据、作者解释、为了讲清而做的推演要分开写，适用范围紧跟相应结论。
- *评测贡献不等于科学发现。* 新 benchmark 让问题可测，不等于解释了现实世界。
- *公式不必全删。* 如果一个公式是最短的关系说明，保留它，下一句立刻翻译成普通话。
- *`source` 不是参考资料列表。* 只放一个最接近论文原文的裸 URL。
- *允许论文没有惊天发现。* 工程改进就按工程改进来讲，不替作者拔高。

## 写作声音

目标是直白，不是幼稚；简洁，不是少讲关键关系。

- 从具体名词和动作开始。写「模型继续生成了 300 个 token」，少写「计算资源出现非必要消耗」。
- 一段只做一件事。遇到一句话同时塞进条件、机制和边界，就拆开。
- 短句为主，但不要把完整句子拆成口号。主语要清楚，读者始终知道是谁做了什么。
- 过渡词只在关系真的变化时使用。「先看」「问题来了」「继续」「到这里」「最后」都可以，但不要按固定格式轮流出现。
- 少用抽象名词连写。能用「看不见、分不清、算不动、贵得用不起」，就不用「可观测性、区分度、计算约束、可达性」开场。
- 机制的缩小版可以开路；装饰性类比放在机制已经讲清以后，只用来压缩记忆。
- 结论直接说。证据有限，就紧接一句「这最多说明什么」，不要另写一段免责声明。

## 结尾：把判断交到读者手里

论文机制在人类处境中存在结构相同的角色、动作和反馈时，结尾可以迁移到工作、关系或生活。迁移不是泛泛写「做菜如此，人生也是如此」，而要指出人在什么处境下做什么、会得到什么结果。它必须保留原机制的作用方向与成立条件，并明确这是应用推演，不是论文直接证明的结论。找不到可靠对应就省略。

最后可以用一句短句压缩全文判断。句中应包含触发条件、判断动作或行动方向，且能从前文完整推出。对称和节奏可以帮助记忆，押韵不作要求；不能为了像警句而牺牲准确性、边界或自然口吻。没有一句真正改变判断的话，就用普通结论收尾。

迁移和短句都自然落在最后一个内容标题下，不另设「人生启示」「金句」等栏目，也不要求每篇论文都有。

## 论文怎么读

完整步骤在 `ReadingGuide.md`。执行时要守住四条线：

1. **起点线**：例子此刻有什么，原来的理解怎样处理它？
2. **改写线**：证据迫使情况、关系、做法或判断尺度中的哪一项改变？
3. **回流线**：改变后的结果怎样成为下一轮的新情况？
4. **证据线**：论文真的测到了什么，哪些只是作者解释或为了讲清而做的推演？

只记住术语不算看懂。读者至少要能说明原来的判断为什么失效、论文改了哪里、同一件事为什么因此得到不同结果；论文测过条件变化时，还要知道结论会在哪里停住，没测过时则知道边界仍未知。

## Quick Reference

1. 判断论文主要改写 `x`、`R`、`f`、`E` 中的哪一项；这是后台标记，不写进正文。
2. 把贡献翻成主角、条件、动作、期待结果、实际结果与最先改变的可见结果。
3. 选一个保留角色、作用方向、反馈顺序和关键条件的机制缩小版。
4. 让读者最自然的理解先运行一次，只写过程和结果。
5. 用论文证据指出一个具体缺口：哪里分错、猜错、做不到或判断不出来。
6. 只改当前被证据逼着改变的那一部分；作用可见时命名，随即回到原例子重跑。
7. 把新结果当作下一轮起点；还有缺口就继续，没有就停。
8. 用论文支持的相近案例、对照或条件变化再跑一次，让适用范围显出来。
9. 按事件、变化和条件生成正文标题；正文写完后再把三问压进 `description`。
10. 若存在结构同构的人类处境，做一次明确标注的应用迁移；没有就省略。
11. 用一句包含条件与动作的短句收束全文；节奏服务判断，不强求对称或押韵。

可见标题不能是分析问题的名字，而要是论文内容本身。例如讲 ReAct，不写「论文解决什么 / 核心发现 / 我的启发」，而可以写：

1. `模型为什么越想越错`
2. `新观察怎样改写下一步`
3. `什么时候工具反而添乱`

这只是三个叙事运动的示例。论文中间有两个真正不同的转折，就用两个内容标题展开；只有一个，就不要硬拆。

## Examples

**评测论文**

标题可以是「两篇论文为什么看起来像一路」「真正被继承的是哪一层」「换掉核心机制以后，还算同一路吗」。

先看两份研究方案。它们都在研究长上下文，主题也很像。按常见的文本相似度来判断，第二份像是在继承第一份。

问题来了：第二份方案把核心机制换掉了。主题相似，却不是同一条技术路线。

要分清这种情况，光看研究什么还不够，还要看关键机制从哪里来。论文把这种关系叫作「机制继承」。把它放回刚才两份方案，原来被混在一起的两种关系就分开了。到这里，读者才需要知道新评测怎样把这种继承关系测出来。

**方法论文**

标题可以是「答案已经对了，为什么还不停」「反馈怎样让计算自己收尾」「哪些题上，早停反而会害人」。

一个模型已经答对了题，但它还在继续推理。答案没有变好，token 却多了三倍。

只告诉模型「想得更久」解决不了这个问题。它还需要知道什么时候继续计算已经没有收益。论文加入了一种根据当前答案判断是否收尾的反馈。再看同一道题，模型在答案稳定后停下来了。

这时再给术语。读者已经知道它解决的不是「怎么想得更强」，而是「什么时候该停」。

## Completion

生成笔记后读回确认：

- frontmatter 完整，包含正文写完后生成的 `description`，文件确实保存成功。
- `source` 只有一个裸 URL。
- 每个顶层标题都在说论文里的具体事件、变化或条件，不是「问题、发现、启示」之类的分析栏位。
- 正文不要求固定章数；若拆分中段，每个新增标题都对应一个真实的因果转折。
- 开头是一个具体小例子，不是领域背景或论文摘要。
- 开头已经跨过熟悉度门：不懂该领域的人无需先学模型名、算法名或指标，就能说出谁做了什么、为何没有得到想要的结果。
- 拿掉术语后，读者仍能说出主角、条件、动作、期待结果、实际结果与哪个结果先变。
- 每个顶层标题下，同一场景都执行一次会改变因果链的动作或接收一次反馈；上一段的具体结果成为下一段的输入。只点名、回忆或用一句过渡带回场景不算贯穿。
- 熟悉场景中的每个承重角色、动作和反馈都能映回论文对象及来源证据；无法映回的因果步骤已经删除或标成讲解者推演。改变论文中的关键条件时，场景结果也按同一方向改变。
- 读者最自然的理解先在例子中运行，并出现论文材料支持的真实缺口。
- 每次改写都由证据触发，并立即在原例子的结果里变得可见。
- 每个承重术语都在作用第一次可见处出现，并立刻回到同一例子，不形成术语表式堆叠。
- 任一段只让读者承担一个新的承重概念；模型型号、数据集名和完整指标没有为了显得全面而进入正文。
- 新结果进入下一轮，而不是停在术语解释；回流一路走到作者的完整发现。
- 论文若直接测试了条件变化，结尾把它放回同一场景并显出边界；若没有，明确写「论文没有测到这里」和待验证问题，不制造推演来凑结构。
- 相近案例、反例或条件变化有论文证据；没有证据的内容不冒充论文边界。
- 正文没有「零号模型」「FX 回流」「x/R/f/E」「第一步/第二步」等内部标签；若论文原文恰好使用同名术语，需明确这是论文概念。
- 句子以具体主语和普通动词为主；一段只推进一件事。
- 每个关键关系旁边都有证据，或明确写成作者解释 / 结构推演。
- 证据和适用范围紧跟相应结论。
- 正文保留支撑关键判断、竞争解释和边界所需的最小证据集，不设数字配额；其余核验材料存在于已保存并读回的证据台账，每项含来源位置、直接结果、所支持判断和取舍理由。不用密度冒充严谨。
- 图表若存在，确实比短句更容易看懂，而且没有夸大论文。
- 若保留公式，下一句已经翻译成人话。
- `description` 能回答「为什么需要这篇、作者多看见了什么、以后怎样判断」，但正文不拿这三问当目录。
