# FindEssence Workflow

把一个目标拆成「括号里的限定条件」与「最后落脚的最小状态变化」，然后把完整分析保存为经过验证的 Markdown 笔记。

## Step 0 — Sufficiency Check

只检查一件事：目标是否存在。

- 用户已经给出目标、产品、角色、制度、行为或概念：直接继续，不追问。
- 只有 `/ljg-is`，没有任何目标：只问一句「你想找哪件事的本质？」然后等待。
- 目标有多种常见含义：采用对当前上下文最自然的含义；只有不同含义会导向完全相反的核心时才问一句消歧问题。

本技能始终回答**目的本质**：「它最终把什么变成什么？」若用户明确问「为什么它是这一类而不是另一类」，差异条件进入括号，核心仍单独输出，不新增恒定的「问题类型」字段。

## Step 1 — 写清真正的问题

标题已经给出目标，不在正文重复目标名称。先写出本次分析为什么容易走偏：

```text
容易误认：{最容易被当成本质的限定条件、优点或实现}
真正问题：{谁或什么，最终从什么状态到什么状态？}
```

「容易误认」必须针对这个目标，不能写「容易被表象迷惑」之类空话。「真正问题」是待回答的状态变化，不提前复述最终核心。

## Step 2 — 写出完整功能句

先不要追求简短。用一句话把目标、场景、主体、质量、方式和完成态都写出来：

```text
[为谁] [在何种场景] [以什么方式] [做到多好] + [让谁或什么发生什么变化]
```

这一步允许冗长，因为后面要有东西可删。若只凭对象名称无法知道它做什么，可以使用稳定常识；只有事实会决定不同核心且把握不足时才查证。

## Step 3 — 把限定条件装进括号

逐项标记以下内容：

| 类型 | 判断问题 | 通常去向 |
|---|---|---|
| 身份/主体 | 为谁、由谁、谁有资格？ | 括号 |
| 场景/边界 | 在哪里、何时、适用于谁？ | 括号 |
| 约束/质量 | 多安全、多快、多便宜、多舒服？ | 括号 |
| 优化量 | 要最大化或最小化什么？ | 括号 |
| 实现/载体 | 靠车、App、合同、算法、门店还是网络？ | 括号 |
| 状态变化 | 谁或什么，从什么状态到什么状态？ | 核心候选 |

把前五类放到全角括号 `（ ）` 中，并放在句首。核心候选必须位于整句最后，让语言的落脚点就是本质：

```text
完整：（主体、边界、约束、方式）核心候选
```

没有必要的限定条件时可以没有括号，不能为了形式编造限定语。

## Step 4 — 剥掉实现与优点

对每个词做三次替换：

1. **换实现**：把车换成别的交通工具、把 App 换成人工、把算法换成规则。若目标仍完成，这个词是实现。
2. **降质量**：让它更慢、更贵、更不舒服。若它只是变差，却仍在做同一件事，这个词是质量或优化量。
3. **换类别**：换成相邻类别。若两者仍共享同一最终变化，不必把差异塞回核心；共享本质是允许的。

把剥掉的内容记在「剥离」中，但不要把每个推理岔路都写进成品。按原因分组，每组写成一个带强调关键词的短 bullet：

```org
- *主体/边界*：{哪些内容只限定为谁、何时或何处}
- *实现*：{哪些载体或方法可以替换}
- *质量/优化*：{哪些内容只决定做得怎样}
- *状态式*：{承受变化的对象}：A -> B
```

只输出适用于当前目标的分组；没有某类内容就省略，不为了凑齐而编造。可以合并相近分类，如 `*主体/边界*`、`*质量/优化*`。最后必须以唯一的 `*状态式*` 收尾，让视线从被剥掉的内容自然落到本质候选。Markdown 笔记使用 `**关键词**`。

## Step 5 — 写成状态式

把核心候选改写为一个最小状态式：

```text
承受变化的对象：A -> B
```

例如：

```text
人：地点 A -> 地点 B
风险承担者：不可承受的大损失 -> 可承受的小成本
信息使用者：不知道答案 -> 拿到可用答案
```

状态式是检查工具，不是最终文案。它必须包含：

- **对象**：谁或什么承受了变化；
- **方向**：从哪里到哪里，或什么被维持、避免；
- **完成态**：怎样才算这件事已经做完。

若目标的工作是维持或防止变化，也写成有方向的关系，例如「易腐坏 -> 保持可用」「可能失控 -> 维持稳定」。

## Step 6 — 压成一句人话

把状态式改写成一个短动词句，优先使用：

```text
把 A 变成 B
让 X 从 A 到 B
使 X 保持 B
阻止 X 进入 B
```

核心默认不超过 30 个 Unicode 字符。长度只是外闸，真正的停手条件是：**再删一个词，就会丢掉承受变化的对象、变化方向或完成态。**

以下内容一律不能单独作为核心：

```text
服务 / 价值 / 连接 / 体验 / 效率 / 安全 / 舒适 / 满足需求
```

它们要么没有方向，要么只说明做得怎样。

## Step 7 — 设计一个可代入的操作实验

示例的目标不是「再解释一遍」，而是让读者在脑中亲自运行本质。先按目标类型选择最自然的代入动作：

| 问题场景 | 让读者怎么进入 |
|---|---|
| 产品 / 服务 | 作为用户使用一次，看任务何时算完成 |
| 技术 / 机制 | 跟随一个具体输入，看它如何变成输出 |
| 交易 / 制度 | 跟随一份钱、权利或风险，看归属如何变化 |
| 学习 / 决策 | 做一次选择、看到后果，再改变下一次选择 |
| 维护 / 预防 | 暂时移除干预，看什么状态被破坏或被守住 |
| 抽象价值 / 判断 | 遇到一件具体事情，决定是否以及如何回应 |

再根据「容易误认」决定实验里要替换什么：误认实现就换载体，误认质量就降低质量，误认类别就换相邻类别。成品严格写成四步：

```org
- *代入*：你是{具体角色}，此刻处在{具体起点与任务}。
- *操作*：你{依次执行或观察 2–4 个具体动作}。
- *变化*：{具体对象}：{具体 A} -> {具体 B}
- *点题*：你刚刚真正完成的是「{逐字写入核心}」；{最容易误认的内容}只是限定或实现。
```

四步缺一不可：

- **代入**必须使用第二人称「你」，让读者成为操作者、使用者或承受变化者。
- **操作**必须出现可想象的具体动词，不能只写「理解」「体验」「发生变化」。
- **变化**把这一次场景中的真实起点和终点写成 `->`，不要照抄抽象占位符。
- **点题**必须逐字包含最终核心，明确「刚才哪一个操作就是本质」，再把实现或质量推回括号。

只做一个贴近目标的实验，不堆案例，不借遥远比喻。读者做完后，应能不用术语回答：「我刚才把什么，从哪里，变到了哪里？」

## Step 8 — 重新接回完整表达

生成两条最终表达：

```text
本质：{核心}
完整：（{限定条件}）{核心}
```

对话交付时先给「本质」和「完整」，再给完整的「代入 / 操作 / 变化 / 点题」四步；不能压回一句旁观式「比如」。Markdown 笔记中先保存完整分析，再在「本质」中落下唯一核心，并在「示例」中保存操作实验。

## Step 9 — 内部终检与两条可见验证

1. **删除测试**：核心还能不能再删？再删若丢掉对象、方向或完成态，则通过。
2. **替换测试**：更换实现方式，核心是否仍成立？若不成立，说明实现混进了核心。
3. **过度压缩测试**：把核心换成「提供价值」「连接供需」等更短说法，是否丢掉可判断的完成态？若丢掉，保留原核心。
4. **非唯一性测试**：相邻事物是否也可能共享核心？允许。只有用户问类别边界时，才把差异条件放进括号。
5. **具象测试**：读者能否从一个普通场景复述谁从 A 到 B，并指出哪个误认被排除了？不能则重写示例。

五道测试都在生成过程中执行，但成品的「验证」不是第二个分析区，只保留最能闭环的两条：

```org
- *替换*：{换掉一种实现，为什么核心仍成立}
- *删除*：{再删哪个核心词，会丢掉对象、方向或完成态}
```

「替换」证明括号与核心的边界；「删除」证明核心已经足够短。过度压缩、非唯一性和具象测试若失败，直接回到前面重写，不把诊断过程堆给读者。Markdown 笔记使用 `**关键词**`。

## Step 10 — 保存 Markdown 笔记

除非用户明确说「只分析」「不落盘」或 `read-only`，否则：

1. 获取 `date +%Y%m%dT%H%M%S` 与 `date "+%Y-%m-%d %a %H:%M"`。
2. 从目标生成 4–20 个有意义字符的文件名片段；空白和 `/\\:*?\"<>|` 改成 `-`，去掉重复连字符。
3. 写入 `~/Documents/notes/{时间戳}--本质-{目标片段}__is.md`。
4. 复制技能根目录的 `Template.md`，替换其中所有花括号占位符。模板规定了元数据、六个一级标题、强调 bullet、操作实验及核心落点，不要自行另造结构。

若没有限定条件，写 `完整：{核心}`，不要保留空括号。

## Step 11 — 验收与交付

写入后必须完成全部检查：

1. 运行 `bun ~/.agents/skills/ljg-is/Tools/ValidateNote.ts "{文件路径}"`；非零退出即修复后重跑。
2. 读回全文，确认对话中的「本质」与文件内 `核心：` 完全一致。
3. Org 输出在可用的 Emacs/Denote 环境中确认：文件名与 identifier 一致、Denote 接受、Notes 索引或 consult-notes 可见、`org-lint` 无阻断问题。Markdown 输出由同一校验器检查 YAML 元数据、标题顺序与 identifier。
4. 最终只报告核心、完整表达、「代入 / 操作 / 变化 / 点题」、文件绝对路径和验证结果；不要把内部五道测试重新讲一遍。

若用户要求只分析，仍执行 Step 0–9，在对话中交付同等完整结果，并明确「未落盘」。

## Failure Modes

- **目标缺失**：问一次目标，不创建空笔记。
- **事实不足且会改变核心**：先补证据或明确假设，不用猜测伪装成定义。
- **核心超过 30 字**：先检查是否仍混有主体、边界、质量或实现；确实不可再删时，保留准确性并在验证中说明，不得绕过校验器冒充通过。
- **格式校验、Denote 或 org-lint 不通过**：修复文件再交付；「文件已创建」不等于完成。
