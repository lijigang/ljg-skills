# UnderstandInUse Workflow

把一个「X 是什么」的问题写成可使用的理解。成品既让读者认清 X 的概念位置，也看见它怎样运作；随后从这套机制中自然推出认知修正与行动判断。

## 理想成品

一个不了解框架的读者读完后，能够用自己的话完成四件事：把 X 与相邻概念区分开，说明 X 怎样产生结果，指出这番理解改变了自己原来的哪个判断，并在真实情境中用它作一次更好的选择。

文章只有一条理解路径。定义让对象站稳，机制让对象动起来，认知变化说明前两者为何重要，行动指导把新的判断带回现实。后一部分必须使用前一部分已经建立的理解，不能并列交卷。

## 后台理解，前台讲解

写作前先在后台把五件事想清楚：

- **定义。** X 属于哪一类东西，靠什么特征与最近的相邻概念分开。形式对象可以给形式定义，但仍要翻成普通话。

- **运作。** 什么进入 X，X 做了什么，什么因此改变。技术对象常表现为输入、关键操作与结果；制度对象常表现为参与者、规则与后果。

- **认知修正。** 普通人最容易把 X 误解成什么。定义和机制讲清以后，哪种旧判断已经不能继续保留。

- **行动判断。** 在什么真实情境中，这番理解会改变读者下一步。要检查什么信号，怎样选择，什么时候说明需要调整。

- **根据与边界。** 哪些是材料或一般机制支持的事实，哪些只是推断，什么情况会使当前解释失效。

这五件事是分析者的准备，不是正文目录。正文不使用「定义、运作、认知改变、行动指导、根据、边界」等字段式标题，也不把它们换成近义词继续逐项填写。

赵汀阳的问题链只作条件性补充。若 X 是制度、平台、角色或规范，再检查谁把哪种做法稳定下来、其他可能是什么、反复使用怎样改变参与者。若这些问题对对象没有真实解释力，就留在后台，不为了哲学完整而写进文章。

前台沿着读者的理解变化展开：

- 从一个真实疑惑、常见误解或实际使用情境开始。人物场景可以用，但不强制虚构主人公。

- 尽早给出普通话定义，并马上用相邻概念或反例划出边界。读者先知道在谈什么，后文才不会悬空。

- 用一个够近的例子把运作过程走一遍。例子必须对应定义里的关键关系，不能只负责热闹。

- 从机制推出认知修正。明确说明原来的哪种看法为什么不够准确，不突然换到更宏大的社会问题。

- 把新判断放进真实决策。指导读者先看什么、怎样判断和何时调整，并说明这与前述机制的关系。

- 根据内容自然收束。可以是一句更准确的判断、一条行动原则，也可以是材料真正留下的未决问题。

标题随内容生长，段落数量可以伸缩。完成初稿后删掉机制段再读行动指导：若指导仍然完全成立，它就是没有使用 X 的万能建议。再检查最后的转折：若删掉前文仍能成立，便应删除或重写，而不是靠问号保留。

## 普通话合同

- 概念名尽早出现。不要为了叙事感让读者走很久才知道文章在解释什么。

- 定义先说上位类别和关键差别，再用例子落地。比喻可以帮助理解，但不能代替边界。

- 一句话推动一个主要变化。连续三个以上抽象名词、过多顿号或分号，通常说明后台清单泄漏到了前台。

- 每段两到四句。段落之间可以是概念递进、因果推进或判断修正，不必伪装成时间故事。

- 少用「首先、其次、此外、综上」。它们只标示排列，不会制造因果和时间。

- 不追求思想腔。能说「一把用来比较方案的尺子」，就不先说「可计算的价值秩序」。

一个不了解框架的读者若不能回答「它是什么—它怎么工作—我以后怎么用」，成品就没有完成。

## 根据合同

输入附带文件、书、文章、URL 或对话材料时，先读取原材料。没有材料时，只使用对象的一般定义与运行条件，并自然说明没有核验哪些具体实现或案例事实。

`#+basis` 记录成品直接依赖的事实根据。由此推出但材料没有直接说明的判断，要在正文中用「这意味着」「由此可以推断」等自然说法标明。传闻、感觉和未经核验的可能性不能写成根据。

## Org 输出合同

复制技能根目录的 `Template.md`，生成：

```text
~/Context/{时间戳}--理解-{目标片段}__is.md
```

- 时间戳使用 `date +%Y%m%dT%H%M%S`；可读时间使用 `date "+%Y-%m-%d %a %H:%M"`。

- 目标片段保留 4–24 个有意义字符；不足四字时增加真正说明主题的词，不用无意义填充。

- schema 固定为 `ljg-is-v5`，标签包含 `:is:act:`。

- `#+definition` 用普通话记录 X 的上位类别与关键差别。

- `#+operation` 记录 X 怎样起作用以及什么因此改变。

- `#+recognition` 记录这番理解修正了哪种旧判断。

- `#+guidance` 记录面对 X 时可执行的观察、判断或选择。

- `#+basis` 简要记录事实基础，不写推断和传闻。

- `#+falsifier` 在后台记录什么事实会推翻当前解释；正文只在理解需要时自然处理，不强塞进最后一段。

- 正文使用两到四个随内容生出的一级标题，全文通常四到十段；正文不使用项目符号或字段标签。

- 结尾由内容决定，可以是判断、原则或真问题，不要求问号。

除非用户明确说「只分析」「不落盘」或 `read-only`，否则保存到 `~/Context`。

## 验收合同

保存后运行：

```bash
bun ~/.agents/skills/ljg-is/Tools/ValidateNote.ts "<Org 文件路径>"
```

验证器通过后仍要全文读回。机械检查只能确认理解骨架存在，不能证明中文已经自然。读回时做四次测试：

1. **名词测试：** 能否一句话区分 X 与最容易混淆的对象？

2. **动词测试：** 能否不照抄定义，讲清 X 怎样让输入、选择或关系发生变化？

3. **认知测试：** 能否说出「原来我以为……，现在我知道……」？

4. **行动测试：** 能否举出一个下次会改变观察或选择的具体情境？若删掉机制段，建议仍然完全成立，说明它只是万能建议。

另外单独检查结尾：它是否只是为了显得深刻而突然提高尺度。若转折没有被前面的定义与机制逼出来，就删除，不补一个更响亮的问题。

最终对话用两三段自然中文交付定义、最重要的认知变化与行动抓手，再给文件路径与验证结果。不要把 Org 的后台检查重新复制成聊天列表。

## 失败边界

- 找不到能区分相邻概念的定义：说明还没有真正回答「是什么」，先缩小对象或补材料。

- 找不到可复述的运作过程：说明只给了标签或用途，没有形成理解。

- 找不到由机制推出的认知修正：不要另造哲学转折，宁可保持朴素。

- 行动指导删除概念名后仍适用于任何事：它是空话，回到机制重写。

- 赵汀阳问题链在对象上找不到现实支点：只保留对象自身的运作，不伪造创造者、反制或未来。

- 校验通过但普通读者仍觉得拗口或转折不成立：以读者反馈为最终反证，重建全文路径，不做局部换词。
